# WP0C architecture boundary corrections

Completed corrective proposal for Architect review, 2026-10-05. Started with a clean working tree at `63fcddc87c91d04b8b8300ef3fadf90a984c2042` (WP0B). This package changes architecture documentation only. Phase 1 remains gated on Architect review; no application code, provider API call, OAuth flow, deployment or push is included.

| Review item | Final correction / implementation consequence |
| --- | --- |
| 1. Event → Campaign cardinality | Changed persistence to one-to-many; removed the proposed UNIQUE(event_id), retained a nonunique FK/index. V1 creation service returns the active primary under the Event lock. Future launch/reminder/reschedule/replay campaigns remain unbuilt. |
| 2. Approval / execution | Approval transaction A persists exact snapshot authorization and audit. Separate idempotent start transaction B creates its target units; later per-target claims dispatch. A survives failure/crash before B; resume exact approval without regeneration/reapproval. A combined button can call them sequentially. |
| 3. Approval invalidation | Snapshot/hash/mode are approval authority; source Event revision is provenance. Typed material paths/values and known validator dependencies decide invalidation. Title/schedule/timezone/delivery/location/price/meaningful registration and used factual claims cannot drift. Material edit preserves immutable history, withdraws affected current authority, supersedes pending work and requires successor/fresh approval. Internal notes/unused metadata do not invalidate merely by advancing revision. |
| 4. Capability / readiness | AUTO or MANUAL execution kind; UNVERIFIED/READY/BLOCKED integration readiness for account/target/environment; SIMULATED/LIVE separately. LinkedIn member/organization automation exists; Event Marketing authorization is unverified. Portal has no assigned kind until its interface is understood. Groups always MANUAL; Page excluded. |
| 5. Conditional validation | Canonical scheduled-event baseline plus contextual attendance facts, then selected-destination requirements. In-person usable location; virtual attendance/registration strategy; ticket/payment/platform identity requirements only for relevant plans. Code emits scoped missing/invalid facts; ask only necessary questions. Local known target validation runs before approval; remote uptime is not a universal prerequisite. |
| 6. Destination rendering | All business-significant per-target content is rendered/reviewed before approval. Afterward only mechanical mappings/serialization/timestamp/enums/multipart/exact asset transport and explicitly approved returned-link binding. Meaningful rewrite/truncation/hashtag/graphic/price/route changes block for new review/approval. |
| 7. Clarification | Deterministic requirement/invalid-value detection → optional AI ambiguity recognition/prioritization/phrasing → concise question. Uncertain/conflicting extraction stays proposed; summary confirmation or focused correction accepts facts. AI cannot invent mandatory fields or overwrite accepted values. |
| 8. COMPLETE | No unresolved required workflow action, not universal success. Completion uses the approved included target set, including not-yet-created units. Success, manual completion/handoff, acknowledged failure and explicitly abandoned uncertainty remain separately visible. Package delivery alone is not task completion. Unresolved UNKNOWN cannot close; explicit risk acknowledgement preserves UNKNOWN evidence and prohibits publish retry. |
| 9. Platform matrix | Eight destinations separate public automation, Event Marketing access, architecture treatment, remaining verification, canonical versus destination facts and Phase 1 mode. Primary documentation supports Eventbrite create/publish, Meetup draft/publish and both LinkedIn author types; exact account access remains unverified. Instagram eligibility/path remains unverified for Event Marketing. Retrieval limits are recorded. |
| 10. Table review | Fifteen retained: each protects lifecycle, authority, immutability, concurrency, provenance or history/query boundaries. Approval differs from version and execution; attempts differ from aggregate target; AI recommendations differ from human decisions. No table added/merged. Nonunique Campaign FK, private Event notes and snapshot dependency metadata clarify existing records. Explicit review is in data-model.md. |
| 11. Phase 1 impact | Same four slices: P1-A persistence cardinality guard; P1-B contextual clarification; P1-C preapproval target validation/rendering/dependencies; P1-D separate durable approval/start, material versus non-material edits, readiness checks and honest outcome accounting. Same four fake publishers and manual Group workflow; no live APIs or added campaign features. |
| 12. Files | Fourteen existing Markdown files modified; two added, listed below. Source audits, evidence ledgers, analysis scripts and all originals preserved. WP0B report retained as historical proposal with an explicit supersession notice. |
| 13. Unresolved | Business routing/registration intent, suggested timezone, immediate-start UI preference/correction behavior and selected-group promotion rules remain the same short client list. Event Marketing live permissions, Portal interface and actual provider reconciliation/publish requirements require later operator/API verification. These do not require new technical questions for the operator. |
| 14. Deferred | Application implementation, real APIs/platform OAuth, full platform schemas, remote correction/edit/delete, reminder/replay features, perfect Group identity resolution, polished/live AI generation and deployment. Existing auth/technology choices are not redesigned. |
