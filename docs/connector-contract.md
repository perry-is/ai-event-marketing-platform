# Destination capabilities and adapter contract

WP0B proposal with WP0C boundary corrections. Registry is deterministic backend configuration, not an AI-created plugin system. An adapter receives an approved semantic plan and immutable assets; platform-specific wire names stay inside it. Unknown capabilities disable that target without breaking intake/generation/review for others.

## Execution kind, readiness and runtime mode

Keep three separate questions in deterministic backend configuration:

- **execution_kind:** AUTO or MANUAL. This is the allowed execution behavior, not account access. Facebook Groups is always MANUAL by product policy. Portal has no assigned kind until its interface is verified, so it is not selectable.
- **readiness:** UNVERIFIED, READY or BLOCKED for a specific adapter/account/target and runtime mode. UNVERIFIED means access/requirements have not been established; BLOCKED means a known reason prevents action (including unavailable access). READY means the configured integration and known prerequisites are usable, not a guarantee that a remote request will succeed.
- **runtime_mode/environment:** SIMULATED or LIVE. Fake adapters may be READY in SIMULATED while the same destination's LIVE access remains UNVERIFIED. These values never upgrade one another.

Declaration also has destination_key, adapter revision, can_render, can_verify, safe_retry_policy (NEVER, VERIFIED_ABSENT, REMOTE_IDEMPOTENCY), supported semantic/asset constraints and success-evidence requirements. Derive can_publish from AUTO + READY + server authorization + active exact approval; requires_manual_action from MANUAL. No additional capability framework/tables or redundant writable booleans.

Public platform automation capability is evidence documented in the [platform matrix](platform-capability-matrix.md); it is not proof of Event Marketing credentials. Eventbrite, Meetup and both LinkedIn identities have documented automation capability. LinkedIn personal is AUTO with LIVE readiness UNVERIFIED, not fundamentally unavailable. Phase 1 retains the four existing fake publishers (Eventbrite, Meetup, LinkedIn organization, Instagram); personal LinkedIn is shown pending access/routing, using blocked/unverified fixtures without adding another publisher. Instagram LIVE remains UNVERIFIED pending exact account/API prerequisites. Groups are MANUAL in both environments; each chosen local group requires usable link/package and human decision. Portal remains UNVERIFIED/nonselectable. Facebook Page is excluded from V1 registry/selection.

No LIVE publishing adapter is activated in Phase 1. A selected UNVERIFIED/BLOCKED target cannot be presented as ready or included in publishing approval; explicitly exclude it and review that distribution intent, or resolve the blocker. The snapshot can preserve informational exclusions/reasons, but excluded targets have no execution unit. Readiness changing after approval blocks that target without deleting approval or silently replacing kind/account/content.

Approval freezes a canonical destination plan separately from the CampaignVersion content snapshot. The backend constructs AUTO/MANUAL treatment and per-AUTO SIMULATED/LIVE mode from trusted server settings/rules; a browser may not choose those values. The exact plan and its independent hash are stored with Approval. At start, dispatch, retry, and reconciliation, connector lookup uses the approved plan entry. Current configuration is consulted only to establish that this exact adapter/mode remains available; if not, the entry is blocked with no mode substitution. Facebook Groups stays one MANUAL package with one completion action and the exact approval-bound selected target set. WP1I-A's test-only Eventbrite LIVE adapter performs no network request and is not production publishing support.

## Layered preapproval validation

Code validates canonical readiness, then each selected destination's known local requirements and business-significant rendered content. For LIVE AUTO, access must be READY and fixed target authorized; for SIMULATED AUTO, the fake integration must be READY and labeled simulated. MANUAL requires intentional human selection, usable target and reviewed package blueprint, not publisher credentials. Static validation runs even if remote APIs are offline. Optional remote validation later is connector-specific; it cannot authorize publishing or rewrite content.

Return structured blockers/warnings with field paths, requirement identifiers and scope (CANONICAL or DESTINATION). Distinguish missing business facts (clarification), unconfirmed/conflicting evidence (confirmation), integration access (operator verification) and content constraints (regenerate/review). Code detects known missing/invalid facts; AI may recognize ambiguities and prioritize/phrase questions, never invent mandatory requirements. The operator is not asked for API permissions as event facts.

Phase 1 fake validators remain synthetic contract fixtures, not complete live API schemas: scheduled-event baseline title/start/timezone/delivery; conditional usable location for in-person/hybrid and attendance/registration strategy for virtual/hybrid; fixed target and reviewed copy/assets. Fake listings may require end/duration; Instagram requires an actual image; Groups require chosen link/package. Price/capacity are required only when the selected intent needs them. A paid Eventbrite plan has additional ticket/payment readiness, whereas a social post need not supply Eventbrite ticket configuration. Real Eventbrite publish readiness also includes ticket classes; the [matrix](platform-capability-matrix.md) distinguishes verified operations from still-unverified complete live requirements. Destination-specific organizer IDs, ticket settings and audience enums belong in the plan, not globally required Event columns.

## Rendering boundary

Before approval, the operator reviews all business-significant per-destination copy, title, hashtags, graphics, audience/semantic settings and manual-package content. The preapproval renderer exposes platform constraints and returns a reviewable semantic payload/blueprint; content generation/revision occurs outside transport execution and creates a new snapshot. No hidden business content is deferred to an adapter.

After approval, only mechanical field-name mapping, JSON serialization/escaping, timestamp formatting, equivalent API enums, multipart construction and exact approved-asset upload are permitted. No rewriting, summarizing, meaningful truncation, hashtag choice, title alteration, creative substitution/crop, price change, content removal or destination choice. An API constraint requiring such a change blocks execution and sends the content back for regeneration/review/new approval; it never triggers silent repair. Declared returned-link slots below are the sole bounded content binding already authorized in the reviewed intent.

| capabilities           | Fixed registry/config and adapter revision.                                                                                                                                                                                                                                                                  | Typed declaration, no network needed; account authorization separately checked.                                                                                                                                                                                          |
| validate               | Candidate snapshot semantic plan and asset metadata.                                                                                                                                                                                                                                                         | Structured errors/warnings and required evidence. Pure local checks; no publishing or copy generation. | render                 | Preapproval semantic plan, immutable assets, declared binding tokens.                                                                                                                                                                                                                                        | Complete review preview and transport/manual-package blueprint. All operations use bounded timeouts and redact diagnostics. Interface exceptions become normalized outcomes in backend code, never a successful result by default. No generic adapter factory accepts source-defined Python/URLs/code. Adapter receives only required data; public assets delivered via short-lived server URLs containing no durable storage credential.

## Normalized result

Envelope: execution_id, version_id, destination_key, target_key, environment, attempt_number, operation, outcome (PUBLISHED/NOT_CREATED/UNCERTAIN/MANUAL_PACKAGE_READY/MANUAL_ATTESTED/BLOCKED/VERIFICATION_RESULT), optional verification_finding (FOUND_MATCHING/CONFIRMED_ABSENT/INCONCLUSIVE), external_id, external_url, human_error, error_category, retryable, occurred_at, verification_status, evidence and adapter_revision. `retryable` is advisory; deterministic policy makes the final choice. Success fields are validated by backend, not copied blindly into protected state.

Backend projects PUBLISHED to SUCCEEDED only after required evidence passes; NOT_CREATED to FAILED; UNCERTAIN to UNKNOWN; MANUAL_PACKAGE_READY to MANUAL_PENDING; MANUAL_ATTESTED to MANUAL_DONE; BLOCKED to BLOCKED. MANUAL_ATTESTED is accepted only from an authenticated human action/reconciliation path, never an AI or publisher adapter's assertion. VERIFICATION_RESULT maps FOUND_MATCHING to qualifying success, CONFIRMED_ABSENT to known failed/no-effect eligible for safe retry, and INCONCLUSIVE to UNKNOWN. A successful verification HTTP request is not a successful publish. Human reconciliation that lacks the adapter's machine evidence is recorded as HUMAN_ATTESTED/MANUAL_DONE, never machine SUCCEEDED; it may account for a found post but cannot establish absence for retry.

Error categories: VALIDATION, AUTHORIZATION, RATE_LIMIT, TRANSIENT_CONFIRMED_NO_EFFECT, REMOTE_REJECTED, AMBIGUOUS_OUTCOME, CAPABILITY, DEPENDENCY, INTERNAL. Verification: NOT_REQUIRED, VERIFIED, UNVERIFIED, INCONCLUSIVE, HUMAN_ATTESTED, SIMULATED. A returned URL alone is not proof. AUTO success needs creation evidence specified by that adapter; if separate verification is required, status stays RUNNING/UNKNOWN until it passes. A mere HTTP send/accepted response is insufficient. Manual completion has HUMAN_ATTESTED, never VERIFIED. SIMULATED evidence is valid only for SIMULATED version/execution; the user sees that label.

External URLs must be valid HTTPS destinations with expected host/path policy before use as clickthroughs or registration bindings. Returned text must not be rendered as HTML. When response cannot establish non-creation, classify UNKNOWN even if the transport error looked retryable. Preserve provider request id and safe error category, never raw token-bearing response bodies.

## Approved registration-link binding

V1 may support one limited mechanical binding: a consumer CTA slot explicitly references a selected registration-producing execution's verified `external_url`. The snapshot names producer destination/target and exact consumer slot; preview says that link will be filled after confirmation. This is an approved semantic instruction, not invented copy. No generic dependency graph engine or automatic route choice is needed.

Validate producer is selected, not consumer itself, no cycles, same version/mode, and chosen registration strategy is DESTINATION_CREATED. Consumer stays BLOCKED until producer has qualifying creation/verification evidence; user may acknowledge blocked disposition if producer fails. Store resolved value and producer evidence in consumer attempt fingerprint. Once consumer publish/package delivery begins its binding cannot change on retry/redelivery. Manual package finalization can substitute this declared textual slot, preserving reviewed copy/graphics otherwise; store its output asset/hash separately without appending to the sealed version manifest. Binding cannot modify graphic pixels or add a destination/category. A new choice/link/copy requires a new version. Real producer return-link behavior remains UNKNOWN; fake adapters prove this contract without asserting platform support.
