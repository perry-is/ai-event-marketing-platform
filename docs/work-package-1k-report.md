# Work Package 1K — LinkedIn Organization connector

**Status: IMPLEMENTED; mocked acceptance passed.** The live adapter uses the accepted mixed-mode Approval and exact CampaignVersion boundaries. Real LinkedIn authorization and account verification remain deferred; no LinkedIn network writes were made.

1. **Starting baseline.** Started from clean `6ecc75ce7752533353e3e112e4402bf4e778982b` (`feat: add live Meetup connector`). The source-integrity check passed before and after implementation.
2. **API version.** The connector defaults to Marketing API `202609`, confirmed current and supported on 2026-10-07. The configured version is validated against the maintained supported-version set; malformed/unsupported values fail closed, including deprecated `202510`.
3. **Access tier.** Community Management access is vetted. Development access is for restricted development/testing; Standard is required for production. The application does not claim that Event Marketing has either tier. A configured tier is an operator-supplied value, not provider evidence.
4. **OAuth architecture.** Organization posting requires member-authorized OAuth. A `LinkedInCredentialProvider` boundary supplies the grant to the adapter. OAuth routes and durable OAuth token handling were not added because the repository has no reviewed encrypted credential store. The default runtime provider is unavailable and fails closed; tests inject a fake provider.
5. **Secure persistence.** No access or refresh tokens are stored in the database. No migration or token table was added. Client secret configuration uses `SecretStr`; credentials are never returned by the Settings API or written to logs.
6. **Scopes.** The readiness boundary checks `openid`, `profile`, `r_organization_admin`, `r_organization_social`, and `w_organization_social`. These support member identity, Organization access checks, and organization posting/readback; no personal-posting permission is requested.
7. **Organization target.** New plans freeze the numeric Organization ID and `urn:li:organization:{id}`. The URN is the identity; configured display name is informational. Existing approvals cannot be redirected by configuration drift.
8. **Role/readiness.** Readiness checks the configured app/tier, credential grant, required scopes, and approved Organization ACL entry for the connected member and exact Page. It reports connector implementation, account connection, configured tier, and live readiness separately. The Posts API and ACL reference disagree on the Content Admin enum spelling; the implementation accepts only the two role names spelled identically by both references and fails closed on the unresolved alias.
9. **Destination plan.** `LINKEDIN_EXECUTION_MODE` is server-controlled through `EMP_LINKEDIN_ORGANIZATION_EXECUTION_MODE`. New plans derive SIMULATED or LIVE and freeze the Page target. The browser cannot submit a mode or Page identity. Old approvals retain their exact mode and target.
10. **REST client.** A dedicated client owns bearer authorization, `Linkedin-Version`, `X-Restli-Protocol-Version: 2.0.0`, timeouts, Rest.li request handling, response parsing, and normalized sanitized errors. Redirects are disabled. Every versioned API request carries the configured version and protocol headers.
11. **Renderer.** Rendering uses only the approved plan entry and exact approved CampaignVersion content. It uses the Organization URN as author, approved copy as commentary, public visibility, and main-feed distribution. It does not use AI, rewrite, or truncate content; copy over the supported limit blocks.
12. **Image upload.** The Images API initializes an upload owned by the frozen Organization, uploads the exact approved PNG/JPEG bytes through the documented raw-byte `PUT` upload flow, then verifies the image resource is `AVAILABLE` and owned by that Organization before creating a Post. Exact version-bound asset bytes are hash/MIME/dimension checked. A newer unapproved asset cannot be selected.
13. **Post creation.** The connector uses `POST /rest/posts`, not deprecated `ugcPosts`. It creates a published organic Organization post with exact copy and optional exact approved image. Text-only approved versions remain text-only.
14. **Readback.** The returned `x-restli-id` is parsed as the Post URN and bound before readback to prevent duplicate create after a lost verification response. Success requires GET of that exact Post and matching author, commentary, visibility, feed distribution, published lifecycle state, and image URN where applicable. No public URL is guessed because the used read response does not provide a verified canonical link.
15. **External binding.** The existing generic `DestinationResourceBinding` stores the local Event, Organization account identity, Post URN, approved content/image hashes, and execution linkage. No LinkedIn-specific table was added.
16. **Copy-only update.** A newly approved copy-only successor updates the existing Post commentary through the documented partial-update operation, then verifies the same Post. It does not create a duplicate.
17. **Media/unsupported changes.** A changed graphic or other unsupported immutable content blocks before LinkedIn mutation. The connector never deletes/reposts to emulate replacement and never silently keeps or omits the changed approved graphic.
18. **UNKNOWN/reconciliation.** A create accepted remotely but lacking a reliable returned Post URN becomes UNKNOWN; ordinary retry is unavailable. A known URN can be read exactly for reconciliation. The connector never fuzzy-matches by text or binds a similar Post. Uncertain image upload prevents Post creation and is reconciled by exact image URN when available.
19. **Retry.** Retries remain destination-local and use the immutable approved mode, Organization, version, and existing binding. A verified success is not repeated, an in-progress execution is not duplicated, and UNKNOWN requires reconciliation.
20. **Rate limits/errors.** HTTP 429 is normalized as retryable for deliberate retry. Authentication, permission, validation, network, server, configuration, and ambiguous outcomes are sanitized into application categories. No aggressive retry loop exists.
21. **Settings/UI.** A protected Settings card reports mode, configured Page, access-tier state, and readiness reasons in plain language. It exposes no client secret, token, authorization code, or raw provider response. Campaign execution distinguishes live verified outcomes, failures, and UNKNOWN from simulated/manual siblings.
