# Work Package 1L Report — Instagram Professional Account Connector

**Status:** WP1L implementation and automated acceptance complete. Real Instagram Login and production publishing remain deferred; no Meta writes were made.

1. **Baseline.** Started from clean HEAD `bbe7ed94eb3879fa8af3cf80c033b2f8002d86cc`. The supplied pre-change baseline was backend 235/235, frontend 51/51, and Playwright 48/48. Final reruns are recorded below.
2. **Instagram Login architecture.** Uses Instagram API with Instagram Login at `graph.instagram.com`; it does not require the Facebook-Page-linked login path. The app uses the Instagram Professional account identity returned for the authorized user.
3. **API version.** Configurable through `EMP_INSTAGRAM_GRAPH_API_VERSION`, default `v26.0`, checked against Meta's current documentation on 2026-10-07. Malformed values fail configuration; there is no silent fallback.
4. **Access tier.** Meta's API availability does not prove Event Marketing app review/production access. Settings and documentation keep connector implementation, account connection, and production readiness separate.
5. **OAuth and credential persistence.** Added an `InstagramCredentialProvider` boundary and a production-safe unavailable provider. Real Instagram Login routes and persisted tokens are deferred because this repository has no approved encrypted-at-rest credential store. No plaintext token persistence was introduced.
6. **Scopes.** The adapter requires only `instagram_business_basic` and `instagram_business_content_publish`. It requests no messaging, comments, insights, or ads permissions.
7. **Professional-account validation.** Readiness checks the authenticated account's numeric `user_id`, username for display, `account_type` (`Business` or `Media_Creator`), required scopes, and publishing quota. Personal accounts, missing scopes, and ID mismatches are not ready.
8. **Frozen account identity.** New server-derived LIVE plans freeze the configured numeric Professional Account ID and display-only username in the Instagram target. Mode, account ID, or credentials are never accepted from the browser as authority.
9. **Plan integration.** Instagram remains SIMULATED by default. `INSTAGRAM_EXECUTION_MODE=LIVE` affects only new proposed plans. Stored Approval plans govern execution; account configuration drift blocks instead of redirecting an old Approval. Campaign content hashing remains independent of runtime mode.
10. **API client.** Added a small Instagram Login Graph client for account/quota reads, media-container creation/status, publish, and exact media readback. It uses the configured Graph version, bearer authorization, bounded timeouts, form encoding, and normalized Graph errors. HTTP 200 responses containing Graph `error` are failures.
11. **Renderer.** Rendering consumes the exact approved CampaignVersion plan entry, exact caption, frozen account ID, and exact primary graphic association. No AI, latest-version lookup, content rewrite, or hidden shortening is used.
12. **Signed media delivery.** The adapter signs a temporary media URL bound to the CampaignVersion ID, asset ID, stored asset hash, issue/expiry times, and a random nonce. Its endpoint is public only to allow Meta's fetch and serves only the bound, hash-verified asset representation. It accepts GET/HEAD, has no directory or arbitrary-path access, and does not require an app session.
13. **URL TTL and logging.** Signed URLs expire after 30 minutes and permit repeated reads during that window. Responses use `no-store`, `no-referrer`, and `nosniff`. Uvicorn access logging is disabled to avoid recording the token path; deployment proxy/CDN logs must also avoid retaining these paths longer than operationally necessary.
14. **Graphic validation and format.** The source bytes are hash-checked, decoded format is checked against stored MIME, and static image dimensions/aspect/size are bounded. Instagram's JPEG requirement is met through a deterministic RGB quality-100 JPEG representation without cropping or resizing. Transparent, animated, oversized, or unsupported images block rather than being silently altered. The approved source file and its identity remain unchanged.
15. **Container creation.** A graphic and non-empty approved Instagram caption are required. Before creating one container, the adapter validates the exact version/Approval, frozen account, credential scopes/account, image, quota, and absence of an existing published resource binding. It passes the signed image URL and exact caption.
16. **Processing.** The adapter checks the exact container status at most five times, with 60 seconds between polls. Only `FINISHED` proceeds; `ERROR`/`EXPIRED` fail, and unresolved processing remains UNKNOWN. No publish call is made for an incomplete container.
17. **Publishing.** `media_publish` is called once, only after the container is ready. A successful mutation response alone is insufficient.
18. **Readback and permalink.** The returned media ID is read back exactly. Success requires exact ID, caption, `IMAGE` type, matching account username, and a verified canonical HTTPS Instagram `/p/{shortcode}` permalink. The application never synthesizes a permalink.
19. **External resource binding.** Reuses the generic destination-resource binding, keyed by Instagram destination, frozen account, and local Event. The verified media ID/permalink and approved caption/graphic identity are retained. Container identity remains operational evidence for reconciliation.
20. **Published-post immutability.** A later approved CampaignVersion for an Event with an existing Instagram media binding is blocked before provider mutation. V1 has no post-edit, delete, or repost path and cannot create a second post automatically.
21. **UNKNOWN and reconciliation.** Uncertain container or publish outcomes become UNKNOWN and are never blindly retried. A known media ID is read exactly; a known container ID is checked exactly. No caption/time fuzzy-search or automatic binding is used. If identity is unavailable, the result remains unresolved for operator handling.
22. **Retry.** Retry is Instagram-only and is permitted only when the service can deterministically establish that publication did not occur. UNKNOWN requires verification/reconciliation first. Sibling destinations and the approved plan are untouched.
23. **Rate and publishing limits.** Readiness and execution consult Meta's publishing-limit endpoint rather than hardcoding a folklore daily quota. Rate-limit responses are normalized; there are no aggressive automatic retry loops.
24. **Settings and execution UI.** Settings now shows Instagram mode, connection/readiness, username when verified, eligibility, and secure media-delivery readiness without exposing credentials or signed URLs. Verified Instagram posts now receive a View on Instagram link only when the URL matches the canonical HTTPS post path. Mixed live/practice/manual states remain per destination.
25. **Meetup compatibility.** Meetup LIVE currently blocks CampaignVersions containing a graphic because its binary photo transport remains unverified, while Instagram LIVE requires a graphic. A single graphic-bearing version therefore cannot be LIVE on both under current reviewed rules. Tests exercise Instagram LIVE with Meetup SIMULATED; neither invariant was weakened.
