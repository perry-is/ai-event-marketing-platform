# Execution identity, retries and uncertain results

WP0B proposal with WP0C boundary corrections. There is no cross-platform transaction or general exactly-once guarantee. The app guarantees it will not intentionally publish twice for the same successful unit, will not retry uncertain remote outcomes blindly, and will preserve what is known. Platform-specific recovery is a later verified adapter responsibility.

## Durable authorization before execution

Approval transaction and execution initialization are separate. Start-execution takes an already committed active Approval and idempotently creates its selected units from the stored plan. A crash before units exist leaves approval resumable, not revoked. Recheck material dependencies and whether each exact approved connector mode remains available at start and dispatch; an outage/config mismatch blocks work without changing the plan or requiring reapproval. Current settings may not substitute another mode. [Versioning](campaign-versioning.md#approval-and-execution-transactions) defines transaction A/B.

## Identity and claim protocol

Logical identity is `(approval_id, destination_key, target_key)`, unique in PostgreSQL. Each unit also freezes its execution kind, the AUTO runtime mode (null for MANUAL), and destination-plan hash. Target is a stable selected publisher-account reference; the single Facebook Groups package has one package target and the exact local Group record IDs/chosen URLs frozen inside its plan entry. Idempotency key is a stable digest of CampaignVersion, destination/target, the approved entry mode and destination-plan hash, not attempt number. Attempt number monotonically increases under the execution lock; it does not create a new remote intent.

1. Authorize the user/system operation. Lock Event, Campaign, then target execution in that order. Any new PUBLISH/PREPARE_MANUAL action rechecks active approval id, both approval hashes, version identity, material-fact consistency (not generic Event revision equality), the mode frozen in this plan entry, fixed account authorization, no cancellation flag, readiness for this exact mode, and legal status. A changed setting cannot turn LIVE into SIMULATED or the reverse. An acknowledged uncertain-abandonment disposition prohibits PUBLISH. Evidence-only VERIFY/RECONCILE and finalization require authenticated authority plus matching historical execution/version/attempt, but not a still-active approval: withdrawing permission must not erase results of requests already sent. These operations can never create a new remote effect. A bare adapter call cannot bypass this service.
2. Check duplicate-submit identity; if already RUNNING return existing operation/status; if SUCCEEDED/MANUAL_DONE return the result. The unique keys handle concurrent clicks, not just disabled buttons.
3. Claim execution by inserting a RUNNING attempt with a durable `lease_expires_at` timestamp, then commit. The attempt identity is the ownership identity. The default 30-minute lease exceeds current bounded connector request/poll flows (including Instagram's bounded processing wait). Claim defines dispatch boundary; concurrent material edits of affected facts are rejected until it settles; unrelated internal-note edits remain allowed.
4. Record possible dispatch before sending, outside a long DB transaction. Execute only this destination/target with its original logical key and frozen request/bindings. No loop over successful siblings.
5. Finalize evidence in a short transaction with attempt id/token check, append audit and recompute campaign disposition. Late generation/network completions cannot overwrite newer records. A late matching response may reconcile its still-unresolved attempt only through the same evidence checks; never through an unconditional status assignment.

Lease expiration does not authorize a second publish. On distribution/status reads and relevant Start, retry, reconcile, or disposition commands, the service checks expired leases and atomically recovers them. An expired PUBLISH attempt becomes UNKNOWN with `EXECUTION_INTERRUPTED`, preserving its attempt and evidence; an expired RECONCILE attempt remains UNKNOWN and is finalized as inconclusive. No provider request is repeated. Unexpired RUNNING work is left alone, including across process startup, so a worker does not claim another worker's live work. This lazy lease recovery avoids assuming that startup means every active execution is abandoned. Verification remains a separate non-publishing operation.

## Retry decisions

| Prior outcome                                                                         | Allowed operation                                                                                                                                                                             |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SUCCEEDED                                                                             | Read/verify existing result. Never another create/publish for this execution.                                                                                                                 |
| FAILED, provider rejection or locally validated error with confirmed no remote effect | Explicit user retry may create next attempt if current approval/account/capability still permits it. Same logical key. Respect server rate limits; no hidden infinite retry loop.             |
| FAILED but absence not established                                                    | Classification must be UNKNOWN; verify/reconcile, not publish.                                                                                                                                |
| UNKNOWN after timeout/disconnect/crash                                                | Verify using provider idempotency record/request id/external id if supported. FOUND_MATCHING records success; CONFIRMED_ABSENT permits later explicit safe retry; INCONCLUSIVE stays UNKNOWN. |
| BLOCKED                                                                               | Retry eligibility after dependency/account condition resolves, without changing approved intent. Target/mode replacement needs new version.                                                   |
| MANUAL_PENDING                                                                        | Redeliver the same package/download without representing a new remote action. Record user completion or skip; backend cannot publish it.                                                      |
| SKIPPED/SUPERSEDED                                                                    | No publish retry. New intent requires new version.                                                                                                                                            |

Instagram SUCCEEDED + LinkedIn FAILED therefore gives a LinkedIn-only retry. It reuses LinkedIn execution identity and creates another LinkedIn attempt; Instagram row and post are untouched. No “retry all” interface. Failed/blocked closure acknowledgement binds to that exact result fingerprint/attempt, not to all future outcomes. A retry or new blocking result clears that failed/blocked acknowledgement; another failure requires another acknowledgement before COMPLETE.

REMOTE_IDEMPOTENCY is not permission to send arbitrary retries: live adapter review must establish provider guarantee, key lifetime, identical-intent/payload requirements and safe behavior after expiry. Phase 1 UNKNOWN always uses evidence-only reconciliation. A later supported idempotent reissue may be a reviewed reconciliation mechanism within its guarantee, never an assumption that a repeated key alone prevents duplicates.

## Timeout after remote creation

If request times out after remote platform may have created content, persist UNKNOWN, with possible dispatch time, request fingerprint, key and request id. Never change it to FAILED merely because the HTTP client timed out. If adapter has no reliable verify operation or remote idempotency guarantee, automatic retry is unavailable. Operator/the operator can provide a found remote URL/id through a controlled reconciliation action; backend validates identity/target evidence where possible and labels any manual assertion HUMAN_ATTESTED. A guess is not confirmed absence.

No generic name/title search establishes absence: provider listing can be delayed, truncated or incomplete. Only a verified adapter-specific absence guarantee or a supported remote idempotency key can authorize reissue. Otherwise leave UNKNOWN, explain that posting may have occurred, and escalate the single target. An authenticated user may attest that a specific matching post was found, supplying target/URL and explicit statement; record MANUAL_DONE/HUMAN_ATTESTED (including for an AUTO target), not machine SUCCEEDED. This accounts for a found effect and forbids republish; a guess or declaration of absence does not permit retry. Unresolved UNKNOWN blocks campaign completion and successor approval; other targets' finished work remains visible. Runtime can keep executing already authorized unrelated units, but cannot hide this unresolved possibility.

Stored attempts distinguish operation PUBLISH, VERIFY, PREPARE_MANUAL, ACK_MANUAL and RECONCILE. Terminal attempt evidence is append-only; reconciliation is another attempt/audit event rather than overwriting failure history. Human-attested AUTO reconciliation records its evidence/verification label distinctly and must meet the selected adapter's policy; it is never machine-verified automatically.

## Explicitly accounting for an uncertain outcome

If verification remains inconclusive, the user may explicitly abandon further action on this exact uncertain attempt, acknowledging “posting may already have occurred.” Record actor/time/reason and result fingerprint in disposition as ABANDONED_UNCERTAIN; preserve UNKNOWN and all evidence. This ends the required reconciliation task, never asserts success or absence, and permanently prohibits publish retry for that unit, even if later evidence changes its status. The completion reducer distinguishes this acknowledged uncertainty from an unresolved UNKNOWN. No automatic timeout/lease/error maps to this disposition. A late qualifying result may still be collected as evidence without another remote effect.

Before any successor targets the same account/group, either reconcile first or require an explicit duplicate-risk acknowledgement tied to that uncertain prior execution plus a reviewed replacement/correction intent. This is never an ordinary retry or implicit bulk republish. Pending remote effects and any delivered package remain visible. An unresolved RUNNING operation cannot be abandoned as settled until its lease/evidence path accounts for possible dispatch. Campaign abandonment stops claims immediately; closing it follows the same required-action reducer.

## Manual action and safe corrections

The single Facebook Groups package carries the approved version/plan hashes, selected Group set and URLs, exact copy/graphics and human instructions. Delivery alone does not complete a required human task. User may explicitly accept handoff responsibility (MANUAL_HANDOFF disposition) for a finished package, or record completion/skip once for the package. Handoff is visible as external manual work outstanding, not published success. Completion command contains version/execution/package hash and attestation; optional post URL is user-reported, not machine success. Duplicate acknowledgement returns current disposition. When a newer version supersedes pending manual work, old downloads display superseded status and cannot be marked as current action; prior manual outcomes remain history.

Successful old versions are not republished on tone/fact revision by default. A successor targeting the same account/group must include a visibly reviewed replacement/correction intent and previous execution reference. V1 implements explicit warning/confirmation, not remote edit/delete. Any eventual remote operation requires separately verified platform contracts.

Database constraints, transaction checks and tests in [test strategy](test-strategy.md) enforce these guarantees. Real APIs that cannot support safe reconciliation remain AUTO with readiness BLOCKED until their safety policy is reviewed; conceptual capability is not erased. The app's mode switch cannot convert a simulated receipt into a live result.
