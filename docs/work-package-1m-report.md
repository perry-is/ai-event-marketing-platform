**Status:** Implementation complete; automated acceptance passed. Real provider authentication remains deferred.

1. **Starting baseline.** The repository began clean at the specified commit. Source-integrity validation passed before implementation. WP1M changes remained local and uncommitted while acceptance was run.
2. **Threat model.** The vault protects delegated tokens from a database-only backup/dump, ordinary database inspection, accidental API serialization, routine logs, frontend state, and Git. It does not claim protection against code execution in the application process, a compromised host, or an attacker with both the database and active key material.
3. **Encryption primitive/library.** Credential payloads use `cryptography`'s high-level AES-256-GCM AEAD API with a 256-bit key and authenticated encryption.
4. **Key provider.** `CredentialKeyProvider` abstracts active-key selection and key lookup. The production file provider validates a JSON keyring and fails closed on malformed or unavailable key material; tests inject an in-memory key provider.
5. **Production key storage.** Configure an absolute `CREDENTIAL_VAULT_KEYRING_PATH` outside the repository and an active key ID. Keep the mounted keyring separately protected and backed up. Startup never creates a key automatically. POSIX group/world-readable keyrings are rejected; Windows ACL protection is an operator requirement.
6. **Credential schema.** One `provider_connections` row stores non-secret identity/status/scope/expiry metadata. One `credential_envelopes` row per connection stores only key ID, payload schema version, nonce, ciphertext/tag, and update time. The versioned payload includes only the delegated access token, optional refresh token, and token type.
7. **AAD format.** `event-marketing:credential:{provider}:{connection_uuid}:{envelope_uuid}:{payload_schema_version}:{key_id}` binds encrypted data to provider, connection, envelope, schema, and key version.
8. **Nonce generation.** Each encryption uses a cryptographically random 12-byte nonce. Repeated encryption of the same plaintext produces different nonce/ciphertext.
9. **Key versioning.** Each envelope records the key ID used to encrypt it. Reads use that recorded key; new writes use the configured active key. A missing historical key fails closed.
10. **Rotation.** `python -m scripts.credential_vault rotate` explicitly locks and re-encrypts records under the active key with new nonces in a transaction. It does not write plaintext to disk or delete old keys. Safe audit/log output contains counts and metadata only.
11. **Provider connection schema.** A unique provider row supports LinkedIn and Instagram, recording owner, provider subject, connected account identity/display name/type, granted scopes, token expiries, connection/refresh/reauthorization/disconnect timestamps, and lifecycle status. No token columns exist.
12. **OAuth attempt schema.** `oauth_authorization_attempts` stores provider, user, current application-session FK, one-way state digest, fixed `SETTINGS` return destination, creation/expiry, and consumed timestamp. State is random and single-use; no PKCE verifier is stored because the implemented confidential server flows do not use PKCE.
13. **State security.** State is generated with 256 bits of randomness, stored only as SHA-256 digest, bound to provider/user/session, expires after ten minutes, and consumed under a row lock before exchange. Callbacks require the same authenticated app session. Duplicate parameters, denial, mismatches, expiry, replay, and provider errors fail with sanitized responses. Redirect destinations are fixed; no open redirect is accepted.
14. **PKCE.** No PKCE is used for these confidential server-side provider flows; the reviewed current provider contracts use client-secret-backed code exchange. The Google OIDC login’s PKCE behavior remains separate.
15. **LinkedIn OAuth.** The confidential Authorization Code flow requests `openid`, `profile`, `r_organization_admin`, `r_organization_social`, and `w_organization_social`. UserInfo verifies the connected member subject. No social write occurs during connection. Account connection alone does not establish Page authorization or Community Management approval.
16. **LinkedIn refresh.** Refresh-token handling is conditional: a returned token and expiry are encrypted; refresh uses LinkedIn’s documented endpoint and is serialized under a PostgreSQL row lock. Rotated refresh tokens replace old material only after success. Apps without refresh-token access require explicit reconnect when needed. Provider 401 marks `REAUTH_REQUIRED` without blind retry.
17. **Instagram OAuth.** The implementation uses Instagram Login, requests only `instagram_business_basic` and `instagram_business_content_publish`, exchanges the authorization code for a short-lived grant and then a long-lived grant, and verifies `/me` identity against the configured Professional account ID and Business/Creator account type. It does not use the Facebook-Page-linked flow.
18. **Instagram renewal.** Refresh is limited to the documented long-lived-token endpoint and validity/age window. Expired/revoked credentials require reconnect. Invalid-token responses mark `REAUTH_REQUIRED`. No claim is made that an OAuth grant proves app review, publishing quota, or full live readiness.
19. **Connector credential providers.** Existing LinkedIn and Instagram live adapters now receive grants through vault-backed providers. They do not query ciphertext tables. Credential retrieval decrypts only for LIVE readiness/execution; Settings uses metadata. Provider 401 callbacks persist reauthorization-required state.
20. **Reconnect.** A new one-time attempt is required. The existing envelope remains active unless exchange, scope validation, provider identity validation, key availability, and encryption all succeed. Successful replacement is atomic; failed reconnect preserves the prior working credential.
21. **Disconnect/revocation.** Authenticated, CSRF-protected disconnect deletes the active local encrypted envelope and marks metadata disconnected. LinkedIn revocation is attempted and status is reported truthfully; Instagram local removal is supported, while provider-side revocation is reported as unsupported by this flow. Obsolete token ciphertext is not retained as active audit material.
22. **Logging/redaction.** Provider response bodies, OAuth codes, access/refresh tokens, client secrets, authorization headers, and key material are not logged or returned. Token-bearing response dataclasses redact `repr`; OAuth callback query logging is disabled for Uvicorn access logs. Reverse-proxy access-log retention needs the documented deployment setting.
23. **Backup/recovery.** A database backup alone cannot recover tokens. Back up the external keyring under separate controls; loss of a required key makes its envelopes unrecoverable. The app does not export keys. KMS/HSM integration is deferred.
