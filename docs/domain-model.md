# Event Marketing domain vocabulary

WP0B proposal with WP0C boundary corrections for Architect review, 2026-10-05. This vocabulary defines product meaning; [data model](data-model.md) defines persistence. **CONFIRMED** requirements come from the current work-package instruction, including “Models reason. Code enforces reality.” **ASSUMED** choices below are engineering proposals awaiting review, not discoveries about the operator's history.

There is no verified historical Events Master. Its approximately 56-record/26-column claim is **UNVERIFIED / POSSIBLY INCORRECT** (EVT-011/014 in [evidence](evidence/observations.md)). Narrative concepts can inform requirements; they establish neither columns nor recurrence. The planner is task/schedule evidence (EVT-009/010), the checklist is reference content (EVT-013), and graphics are qualified creative evidence (VIS-001–003).

## Event versus Campaign

“Make LinkedIn warmer” creates a new Campaign Version with revised LinkedIn copy and the same accepted Event facts. “Move the event to 4 PM” proposes a fact change; the backend requires explicit user confirmation, advances Event revision and withdraws current campaign authorization. A conversational request never grants approval implicitly.

Source quotations and model suggestions are evidence, not validated facts. “Free lunch” printed on a reference graphic does not become an organization default. Group “Done” administration notes are not posting permissions. Exact source rules and exceptions remain traceable without forcing the operator to operate an audit system.

The primary screen shows the Event summary, the campaign she is reviewing, and a compact destination outcome list. IDs, attempts, retries, leases and payload fingerprints belong behind that experience.

Persistence permits later launch/reminder/reschedule/replay campaigns for the same Event; none of those extra workflows is being built. An internal note or administrative metadata edit may advance Event revision without altering approved intent. Code compares material facts and dependencies under the [versioning rule](campaign-versioning.md#material-versus-non-material-change); it never asks a model whether approval remains valid. COMPLETE means no unresolved required workflow action, with success/manual/acknowledged failure outcomes distinguished.
