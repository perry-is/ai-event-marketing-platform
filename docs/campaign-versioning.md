# Campaign versions and approval

WP0B proposal with WP0C boundary corrections. Event is accepted business truth; Campaign is the work of presenting/distributing it. Persistence allows many Campaigns per Event; V1 exposes one active primary campaign, each with an ordered sequence of immutable versions. A Campaign Version is inserted only when a complete review snapshot exists. Revision of any snapshot content creates another version, including revisions before approval. Existing snapshots are never edited or deleted by the application.

## Assembly and review

1. Capture Event revision and campaign revision/request token; process only supplied sources and confirmed facts.
2. Generate/compose content and immutable creative assets; derive destination semantic plans and preapproval previews/manual-package blueprints. Run canonical and selected-destination local validation for factual consistency, chosen targets, credentials-free payloads, known platform constraints and execution kind/readiness. If a declared returned-link slot is used, preview displays that explicit pending slot; all other content/graphics must be actual reviewed output.
3. Insert snapshot, asset manifest and audit record atomically if captured generation inputs still match. Event revision is a concurrency/provenance token here; later non-material edits do not invalidate approval. Stale generation cannot become the current review.
4. The operator reviews the actual copy/graphics/destinations/groups, not an abstract “looks good” summary. The backend preview shows the server-derived treatment and safe target label for each target: LIVE, SIMULATED, or MANUAL. Missing selected-destination content/asset or genuine required fact is a blocker. Deterministic, accountable successor limitations may remain included for explicit approval and later accounting, but are shown as “Cannot publish automatically,” never as publishable. Target intent changes require renewed approval.

The snapshot includes Event facts used and evidence references, generated listing/social content, distribution/account/target choices, selected groups and their chosen URLs, graphic bytes by immutable hash/reference, destination semantic fields, exact manual-package blueprints, validation summaries and useful generation metadata. Historical source bytes remain separately preserved. No model promise substitutes for rendering the reviewed creative asset. A final mechanical package incorporating a declared execution-output link is separately hashed/recorded as an execution output; it does not modify snapshot content or its asset manifest.

## Exact approval rule

Only an authenticated, enabled app user may approve through an explicit confirmation control. Conversational revisions and AI tool output are never approval. Approval binds two independent values: the CampaignVersion content hash and the server-derived destination-plan hash. The content hash does not contain connector execution modes. “Fake approval” must not mean bypassing the exact-version/plan rule.

The approval command supplies expected CampaignVersion ID, snapshot hash and Campaign command revision, plus `expected_destination_plan_hash` from the preview and legitimate selected-target intent where that exists. The browser never supplies plan contents or runtime modes. Backend locks Event then Campaign, derives each AUTO mode from trusted server configuration, fixes MANUAL policy/targets, canonicalizes and hashes the proposed plan, and compares that hash to the expected preview hash before creating Approval. A mismatch returns `APPROVAL_PLAN_CHANGED` (HTTP 409) without approval; the user must review the refreshed preview and explicitly approve again. The backend also checks current review ownership, immutable manifest/hash, material-fact consistency, canonical/selected-destination readiness, authorized fixed target identities and no RUNNING or unresolved UNKNOWN predecessor work. Source Event revision stored in version/approval is provenance; it need not equal the current Event revision. Approval authorizes only this exact included destination plan. No approval authorizes a successor version or a different plan.

The immutable Approval stores the exact destination plan and its hash alongside the exact CampaignVersion ID/content hash. Equivalent plans hash identically; a mode, target, or other execution-significant change changes the destination-plan hash. Approval rows are not unique by `(version, plan hash)`: if another plan supersedes an authorization and configuration later returns to an earlier plan, that earlier plan still requires a fresh approval record rather than reactivating historical permission.

Known static/local destination constraints run before approval; remote uptime is not a universal review prerequisite. If required information is missing, code emits the gap and clarification is needed. If account access is unverified, the user can explicitly exclude that target and review the resulting plan; the system cannot silently drop it. At least one executable AUTO or intentional MANUAL target must remain. A later temporary access/API failure blocks execution while preserving approval, rather than pretending approval failed.

## Approval and execution transactions

1. **Approve (transaction A):** persist immutable Approval, current active pointer, APPROVED state and audit atomically. No execution rows or network call are required to commit approval. A repeat command for the same still-active version returns that Approval; it never reactivates a withdrawn/superseded approval.
2. **Start execution (transaction B):** receive the existing Approval ID; verify the exact CampaignVersion hash and stored destination-plan hash, then recheck active authority, material dependencies, cancellation and readiness under locks. Insert exactly the included per-target execution units from the stored plan; current configuration can make an approved mode unavailable but cannot replace it. Repeated commands reuse those units. No remote call occurs in B.
3. **Dispatch (later per-target claims):** claim only eligible units using the [execution safety](execution-safety.md) guards. The campaign becomes EXECUTING when an attempt begins or a manual package is delivered; merely creating units does not prove publication.

A UI “Approve & Publish” command may call A then B then dispatch, but these are separate deterministic domain actions. If B fails or the process stops after A, the campaign stays visibly APPROVED, “Distribution not started.” Resume B against the same Approval; do not discard approval, run generation or demand fake reapproval. Concurrent/repeated starts create one unit per exact target. Failure of one dispatch does not roll back A or siblings.

The currently configured destinations default to SIMULATED, while Facebook Groups remain one MANUAL package. The architecture permits a future destination to use LIVE alongside simulated and manual targets under one Approval. WP1I-A proves this boundary only with a no-network test adapter; it does not activate a live connector. Immediate start is a UI choice; approval and execution remain separate backend actions regardless of button wording.

## Material versus non-material change

| Change                                                                                                                                                     | Treatment                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Title, date/time/timezone, delivery, venue/address/join instructions, price/registration strategy or substantive facts                                     | Material when represented in approved intent or affecting its readiness. Confirm edit, increment Event revision, withdraw affected active approvals, require successor assembly and fresh approval.                                                         |
| Copy, headline, CTA, graphic bytes, layout that changes reviewed appearance, target/account, selected group/link or substantive semantic platform settings | Material. Facts stay unchanged unless explicitly edited; withdraw active approval and create successor snapshot requiring approval.                                                                                                                         |
| Retry counter, safe diagnostic/error metadata, attempt timestamps, verified returned ID/URL or manual completion                                           | Non-material result/history update; no snapshot edit and no new approval.                                                                                                                                                                                   |
| JSON escaping, API field-name mapping, multipart boundary, temporary signed asset delivery URL                                                             | Non-material only when mechanical and semantics/assets are identical to approved plan. Record adapter revision/request fingerprint. Changed crop, content truncation, privacy/audience, price rounding, substituted asset or inferred category is material. |
| Runtime capability/account access changes                                                                                                                  | May block execution. Cannot silently switch AUTO to MANUAL, change account or drop a destination; new intent needs a new version. A disposition can mark original target skipped, without authorizing a replacement.                                        |
| Resolve a declared returned-registration-link slot                                                                                                         | Non-material only for the explicit typed binding reviewed in the snapshot; no new choice/copy. Binding value/evidence is recorded in execution attempt. Arbitrary post-approval link insertion is material.                                                 |

**Deterministic material invalidation:** each snapshot records material field paths and values used for public facts, factual claims and validator dependencies. Code supplies mandatory dependencies for title, start/end when used, timezone, delivery, usable location/attendance plan, price and meaningful registration facts, plus all accepted factual inputs used in copy/graphics/selected destination semantics. No model can remove a dependency; generation cannot introduce unsupported factual claims. Compare accepted before/after values with those snapshot values/dependencies using typed normalization (not fuzzy AI equivalence). Removing/altering one, or making its known readiness invalid, is material.

In the edit transaction, preserve immutable version and historical Approval; clear affected Campaign active approval pointers, append SUPERSEDED audit reason/changed paths, mark undispatched/pending manual units non-executable, and require a successor version with fresh approval. This also applies when approval exists but transaction B has not yet created any units. Never publish obsolete intent by comparing only the old hash.

Internal notes, administrative metadata and unused optional facts with no approved claim/readiness dependency are non-material; increment Event revision and audit without clearing approval. Provenance corrections that change no accepted value may likewise remain non-material. A newly introduced/unclassified factual field defaults to material until its dependency treatment is explicitly defined in code. Dispatch/approval check the material paths against current facts and withdrawal history, not a blanket current-revision equality. Generation can conservatively discard stale input, but must not destroy a prior approval just because revision differs.

## Supersession and races

Beginning a material revision atomically clears active authorization for each affected campaign, sets it DRAFT and marks undispatched predecessor units and not-yet-attested manual work SKIPPED with SUPERSEDED reason/audit. It preserves previous versions, approvals, delivered package evidence and results. A dispatch racing an edit shares the Event/Campaign lock; if an affected attempt was already claimed, a material edit is rejected until it settles. Non-material edits need not wait. If a crash leaves UNKNOWN, draft notes may be preserved, but affected material fact changes/new approval cannot proceed until reconciliation accounts for the old intent or the user explicitly abandons its uncertain outcome under the risk guard in execution-safety.md. Abandonment is not proof of absence and cannot authorize a retry. No cancellation can recall an already dispatched remote request or a manual post performed outside the app.

Previously successful posts remain historical remote effects. V1 does not automatically edit/delete them or republish a correction: a successor displays prior effects (including packages already delivered even without recorded manual completion) and requires an explicit replacement/correction intent before another publish/package to that target. This warns the operator that unrecorded manual posting may already have occurred. Phase 1 demonstrates that guard with fake output. Remote update/delete semantics remain UNKNOWN and outside Phase 1.

“Make LinkedIn warmer” must therefore produce a successor with unchanged facts and explicit LinkedIn replacement intent if an earlier post succeeded. Instagram is not republished merely because it appears in historical context. New version plans select only intended new work; history is still visible. [Execution safety](execution-safety.md) defines per-unit retries.
