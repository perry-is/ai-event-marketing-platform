# Proposed relational data model

WP0B proposal with WP0C boundary corrections; PostgreSQL, one organization, no tenant/organization abstraction. UUID primary keys unless noted, UTC `timestamptz` audit timestamps, restrictive foreign-key deletion for historical records. Mutable rows have `created_at`, `updated_at` and integer revision; append-only rows have creation timestamps. JSONB has an explicit document schema version and backend Pydantic validation. Required query/concurrency fields remain relational. This is a contract, not implemented ORM or migrations.

Clarification and extraction proposals live in bounded Event/source JSON; accepted changes and revision requests are audited, not a full chat archive. Singleton organization display/config lives in server configuration, without secrets in Git.

## Ownership and transactional constraints

Campaign `(id, review_version_id)` references version `(campaign_id, id)`; `(id, active_approval_id)` references approval `(campaign_id, id)`. Both pointers may be null and are assigned only after child rows exist. Approval independently binds the immutable CampaignVersion content hash and a canonical destination-plan hash. Its source Event revision is provenance; current material facts/readiness must still match approved intent. A different current Event revision alone is not a blocker. These cross-record prerequisites are checked while locking Event then Campaign; execution dispatch additionally locks the target execution, always in that order. Event changes lock all affected Campaigns in stable id order; no approved campaign with materially obsolete facts remains executable. DB checks/triggers defend immutable rows and cross-campaign manifests; a deferred exact-set manifest check at transaction end requires relational asset roles/IDs/hashes to match the immutable snapshot, preventing later manifest additions. Runtime DB role cannot disable triggers or change schema; migration role is separate.

Event has a nonunique one-to-many Campaign relationship. Under the Event lock, the V1 creation command returns the existing active primary campaign rather than creating another; it can create a replacement after abandonment. No reminder/replay campaign feature or campaign-kind taxonomy is introduced.

Approval commits its immutable record, active pointer, APPROVED state and audit in transaction A. A separate start-execution command commits the exact selected per-target units idempotently in transaction B. Failure of B leaves A intact; resumption never asks for fake reapproval. Each attempt is claimed in a later short transaction. See [approval boundary](campaign-versioning.md#approval-and-execution-transactions).

No network call is made while holding a transaction lock. Persist the claimed attempt first; finalize evidence in another transaction. Generation holds a token and captures input revision: stale completion is discarded, never silently overwrites a newer intake/revision request. [Execution safety](execution-safety.md) specifies recovery.

## Canonical Event representation

An Event is one occurrence, not a recurring series. A rough draft requires no completed form. Canonical readiness and selected-destination readiness are separate layers. The small event-campaign baseline is accepted title, start with timezone, and delivery for a scheduled occurrence; contextual attendance/registration requirements apply only to the current event and distribution plan. A preliminary draft/preview can remain incomplete. No destination may force irrelevant fields on all other events.

CONFIRMED means supported and explicitly accepted for this event, not independently audited real-world truth. Proposals and known blanks remain distinct. Assumptions that affect claims/routing/scheduling must be confirmed or omitted before approval. No arbitrary 26-key schema or completeness target is imposed.

## Layered validation and clarification

Canonical validation checks the baseline and relevant accepted facts: schedule validity/DST, delivery, factual consistency and a usable attendance plan (location for in-person/hybrid; join or registration strategy for virtual/hybrid). Explicit “location to be announced” is acceptable only if the selected plan/validator supports it. No invented end time, fee or location. Ticket classes, payment settings, platform organizer/group identifiers and audience enums belong to destination plans; they are not globally required Event fields.

Each included target must independently pass known local semantic/content/asset requirements. LIVE AUTO additionally needs READY Event Marketing access; intentional MANUAL needs a valid finished-package blueprint. UNVERIFIED/BLOCKED targets must be visibly excluded from this execution, or the approval is blocked. Missing facts return structured field paths/reasons from code; optional AI prioritizes/phrases questions. Low-confidence or conflicting proposals remain visibly unconfirmed until the concise summary or a focused correction is accepted. See [adapter contract](connector-contract.md).

## Snapshot structure

`snapshot` contains schema version; Event id/source revision and the exact public facts used; material fact paths/values and validator revision; evidence references; listing/social content; selected destination/target identities and approved semantic values; exact selected group display/link/rule context and human decision IDs; immutable asset IDs/hashes and manifest; approved semantic URL bindings if any; canonical and per-target content/readiness validation results and explicit excluded-target reasons; generation model/prompt revision/input hash or SIMULATED generation provenance. Connector runtime mode is not part of this CampaignVersion snapshot or its content hash. At approval time, the backend derives AUTO/MANUAL treatment and per-AUTO SIMULATED/LIVE mode from trusted server configuration and freezes them in the destination plan. The independent destination-plan hash includes execution-significant plan values and exact manual target identities, but excludes readiness text and timestamps. Preserve stored snapshot bytes and plan snapshot as well as their hashes; do not rehash historical documents using evolving serializers.

Version JSON IDs have no automatic FK enforcement; service validates source/group/decision references exist and belong to expected inputs before insertion. Asset manifest and relational ownership are database-enforced. No deletions of referenced sources/assets through ordinary user actions; retention exceptions use explicit operator procedure and tombstones, discussed in [source handling](source-material.md).
